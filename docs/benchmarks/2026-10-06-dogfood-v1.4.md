# Dogfood benchmark — v1.3.2 vs v1.4.0 vs raw Playwright (2026-10-06)

> **Historical report (measured on 1.3.2 / 1.4.0).** Current figures, re-run on 1.7: [v1.7 suites](2026-10-06-v1.7-suites.md) and [competitor comparison](2026-10-06-competitors-v1.7.md).

Raw per-run data and console tables: [`raw/2026-10-06/`](raw/2026-10-06/). Reproduce with `scripts/dogfood/` (see bottom).

## Protocol fields (per `docs/benchmark_protocol.md`)

| Field | Value |
|---|---|
| Date (UTC) | 2026-10-06 (18:30–19:30) |
| Code under test | branch `feat/v1.4-dogfood-overhaul` (release SHA = tag `v1.4.0`); baseline = tag `v1.3.2` in a separate worktree |
| Environment | macOS 24.6 arm64, Python 3.12.12, Playwright 1.58.0, bundled Chromium, **headless** for all runs below |
| "Planner" | **No LLM.** A scripted *oracle model*: for each step it may only act on an action *visible in the text the tool showed it*, picked by label regex (what a competent model would choose). ## 1. Local hard-pattern suite (27 runs per method)

Patterns: cookie overlay, shadow-DOM login, cross-origin iframe payment, custom (div) date dropdown, SPA with delayed render,
search → read price, lazy feed (item 35), hover menu, 6 identical "Add to basket" buttons.

| Method | Success | Median wall | Median tokens read |
|---|---:|---:|---:|
| sb v1.3.2 | 12/27 (44%) | 4,114 ms | 204 |
| raw Playwright (aria snapshot) | 21/27 (78%) | 556 ms | 137 |
| **sb v1.4.0** | **27/27 (100%)** | **436–448 ms** | 159 |

v1.3.2 fails 5 of 9 scenarios (0/3 each): cross-origin iframe payment (`Card number` never offered), shadow-DOM login (`Username`
never offered), custom div date dropdown (`17` not offered), lazy feed (item 35 not offered / no way to scroll to it), and the six duplicate
buttons (clicked the first one). Its settle also costs ~4 s per step, hence the 4.1 s median.
Raw Playwright fails 2 of 9 (0/3 each): the lazy feed (item 35 is not in the snapshot until scrolled; the harness's "classic agent" gets no
hint to scroll, which sb provides via `… more below`) and the duplicate buttons (role+name refs are ambiguous).
The tiny fixtures flatter every method's token count; the real-site table is the fair token comparison.

## 2. Real sites (16 runs per method)

| Method | Success | Median wall | Median tokens read (range over sites) |
|---|---:|---:|---|
| sb v1.3.2 | 14/16 (88%) | 4,492 ms | 844 (538–1,206) |
| raw Playwright (aria) | 11/16 (69%) | 1,340 ms | **15,473** (2,614–**142,731**) |
| sb v1.4.0 default (budget 5000) | **16/16** | 1,432 ms | 2,549 (1,830–3,799) |
| sb v1.4.0 `--budget 2500` | **16/16** | 1,521 ms | **1,326** (1,294–1,978) |
| sb v1.4.0 `--lite media` | 16/16 | 1,412 ms | 2,556 |
| sb v1.4.0 `--lite max` | 16/16 | 1,599 ms | 2,550 |

Reading the table honestly:

* **Speed:** v1.4 is ~3× faster than v1.3.2 (settle rewritten: event-driven DOM-quiet + network-quiet instead of fixed polling).
  Raw Playwright is a little faster per step but fails 5/16 here because the model-visible text is 15k–140k tokens and refs are ambiguous
  (GOV.UK/Amazon/GitHub failures are `no_match` / wrong page). Amazon is the slowest site for every method (2.7–5.3 s for sb).
* **Tokens:** v1.4's view is **~3× bigger than v1.3.2's** (2.5k vs 0.8k) — the price of showing *all* the options (v1.3.2 truncated to
  top-25 actions, which is consistent with it missing shadow-DOM, cross-origin-frame and lazy-loaded targets in the local suite). It is still **~6× (median) to ~55× (Hacker News) smaller than raw Playwright**.
  `--budget 2500` halves it with identical success on this pack; the default stays 5000 because content-reading tasks that sit deep in a
  page weren't represented in my 8 tasks. Use 2500 for cheap/simple loops and `scroll`/`find` for the rest.
* **v1.3.2's two failures** are both BBC Sport (the `Football` link was not in what it showed the model; the cause was not investigated further).

## 3. Page-load benchmark (`navbench`, 8 URLs, median of 3)

Time to a *usable result* and tokens the agent must read.

| Method | warm cache | cold cache | tokens read |
|---|---:|---:|---:|
| httpx (no JS, raw HTML) | 36 ms | 39 ms | 38,842 |
| Playwright `load` | 212 ms | 274 ms | 5,373–7,054 |
| **sb v1.4.0** | **303 ms** | **438 ms** | **1,280** |
| sb `--lite media` | 345 ms | 413 ms | 1,280 |
| sb `--lite max` | 336 ms | 423 ms | 1,285 |

* An **already-warm headless Chromium** gets within ~100–200 ms of Playwright's own `goto` while handing the model ~4–5× fewer tokens
  (and ~30× fewer than the raw HTML httpx returns). It is not "as fast as httpx" for fetching bytes — httpx can't run JS (Wikipedia
  HTML alone is 325k tokens) — but the *model-visible* round trip is ≈0.3–0.5 s.
* **Lite mode is not proven.** Warm: slower (noise); cold cache: 413–423 ms vs 438 ms (within noise); real-site matrix: no speed-up.
  Per the project rule "don't revert until benchmarks prove", it ships **opt-in and off by default**, and the claim "lite is faster"
  is *not made*. Not tested: bandwidth-limited networks, where it should help.

## 4. Gated sites (a logged-in Chrome profile over CDP, read-only)

Attached to a live, logged-in Chrome (own tab only, no clicks that change state, no bets, nothing sent). All via the `sb` CLI:

| Step | Wall |
|---|---:|
| Paddy Power home (cold daemon + attach + load) | 2.4–3.9 s |
| `click "Football"` ambiguous → candidates listed | 75 ms |
| `click 14` → Football page with matches/odds/prices | 1.2 s |
| Gmail inbox cold SPA load (logged in, 900+ unread) | 5.6 s |
| Gmail `type … --enter` (search) | 0.9 s |

Findings that **fixed bugs** (all with regression tests): (1) the tab line leaked the titles of all the person's other tabs and popups from
unrelated tabs could have been adopted; (2) Angular-style wrapper elements with an `onclick` property were listed as giant fake buttons;
(3) labels such as `click Football` errored instead of resolving. Not done: logging in (the profile is logged-out for Paddy Power; I did
not drive the password manager), and no betting actions.

## 5. CAPTCHA (Google's public reCAPTCHA demo, headless, throwaway profile)

* Detection: `recaptcha/checkbox` → `captcha open` → **real image challenge detected** (4×4 and 3×3 grids with prompt text), annotated PNG
  with red numbered tiles (+ optional PDF) produced in ~0.2 s; I read the PNG and chose tiles; `captcha select`/`submit` worked;
  Google served a second round ("crosswalks") which the pipeline detected and re-annotated.
* **Not claimed:** that automation passes reCAPTCHA end to end. Google decides risk from the browser, the headless fingerprint and
  behaviour, not just from the answers; harder providers (hCaptcha, Arkose, DataDome) are untested; many sites' terms forbid solving CAPTCHAs
  with automation. This is for testing your own sites and accessibility-style assistance with a human's consent.
* Bug found and fixed here: `<input type=submit id=recaptcha-demo-submit>` was reported as a "text CAPTCHA", outranking the real checkbox.

## Known limitations / follow-ups

* View is ~3× larger than v1.3.2's; a "brief" mode (changed lines only after non-navigating actions) and folding the repeated sidebar chrome
  after in-site navigation (seen on Paddy Power: ~50 menu links before the content) would cut that.
* HN takes ~2 s for a two-step task although its front page loads in 150 ms with httpx and raw Playwright needs 1.3 s; the extra latency is not yet profiled.
* Oracle models are an upper bound for "dumb model" behaviour; no actual weak LLM was run in this pass.
* One machine, one network, 2–3 reps: treat differences under ~15 % as noise.
